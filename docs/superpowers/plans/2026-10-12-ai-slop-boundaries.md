## A. 边界限定

### A1. 全局不变量：slop 审计不得触碰的九条边界

这些是**项目的安全与正确性边界**。审计可以指出"实现方式有问题"，但**不得**建议删除、简化或跳过它们。每条都有权威出处，碰撞时以出处为准。

| # | 不变量 | 权威出处 |
| --- | --- | --- |
| I1 | 展示目录不是交易真值；价格、库存、订单状态、所有权一律由 Python 交易边界重算 | `AGENTS.md` 边界章节；ADR 0005 |
| I2 | 结账必须在事务内锁定/原子更新库存，并保存价格快照；任何失败回滚全部业务写入 | `AGENTS.md`；`docs/agents/commerce-contract.md` |
| I3 | 创建订单必须要求幂等键；重复请求不得产生第二个订单 | 同上 |
| I4 | 只允许 `MockPaymentProvider`；不得扣款、不得推进为 `paid` | `AGENTS.md`；`docs/agents/commerce-contract.md` |
| I5 | 客户端不得决定 Session 所有权与身份；服务端生成、HttpOnly 传递 | `AGENTS.md`；`docs/agents/open-issues.md` |
| I6 | 未配置可信代理时不得采信 `x-forwarded-for` | 同上 |
| I7 | AI 护栏必须有界：TTL、容量、key 长度/字符集、请求体上限 | 同上（P1-B） |
| I8 | 生产必须验证 TLS 服务器身份；不得默认关闭校验 | 同上（P1-A） |
| I9 | 展示层 `Price.amount`（JS 浮点）不得回流到交易计算；交易侧用 `Decimal`/`Numeric(12,2)` | 同上（P2 金额） |

**操作化判据**：一条发现如果要成立，必须**不要求修改上述任何一条**。若确实认为某条边界本身有问题，写成独立的「边界质疑」条目，**不混入 slop 清单**。

### A2. 禁止标记清单（逐字注入每个子智能体）

以下模式看起来像 slop，实际是硬要求，**一律不标记**：

- guardrails 的 TTL、容量上限、单 key 长度/字符集、单 Session 历史上限、请求体上限与字段白名单。
- 服务端 Session 生成与 Cookie 属性（HttpOnly/SameSite/Secure）、可信代理 IP 判定。
- TLS 校验、`sslmode=verify-full`、preflight 的 production 通则。
- Python Pydantic `response_model` 与响应校验；TS 侧手写解析器（替代 `as T`）。
- 结账重新读取价格与库存、幂等键、事务边界与回滚、订单价格快照。
- `MockPaymentProvider` 与"支付未开放"提示。
- 双层 repository 薄壳（ADR 0002）、共享领域层 `src/domain`（ADR 0005）、幂等建表 DDL（ADR 0003）。
- demo 种子数据与占位商品内容。

### A4. 跨区连带性规则（重要）

一个区的 slop 常常牵连另一个区。规则：

1. **只报本区证据。** 不在本区文件内的代码，不得作为发现的证据，只能作为 `pointer`。
2. `pointer` 的形态是**一行**：`pointer → <目标区号> | <文件:符号> | 一句话说明牵连关系`。不要展开分析。
3. **不直接联系其他智能体**——原因见 C1。所有 pointer 由父智能体归集与转发。
4. 收到别区 pointer 的 agent **只做汇报，不回复**：把它并入自己的发现清单，不反过来质问来源。

### A5. 排除项

- 生成物与金标：`package-lock.json`、`drizzle/**/meta/**`、`backend/data/catalog.json`、`src/server/catalog/data/supplier.json`。
- 二进制与字体（175 个）。
- 第三方代码：`node_modules/`、`backend/.venv/`、`.next/`。
- `docs/superpowers/plans/**` 中**历史计划**的执行状态（历史文档不要求与当前一致，只报"会误导"级别的问题）。

## B. 双批次工作流设计

### B1. 角色与模型

| 角色 | 批次 | 模型 | agent | 职责 |
| --- | --- | --- | --- | --- |
| **发现者** ×14 | 一批 | `dimeta-openai/gpt-6.1-sol` | `reviewer`（只读） | 在自己区里找 slop，产出结构化发现 |
| **分析者** ×N | 二批 | `dimeta-domestic/deepseek-v4.1-flash` | `reviewer`（只读） | 分析发现背后牵扯的不变量/契约/测试/其他区 |
| **编排与仲裁** | — | 当前会话模型 | 主智能体 | 分派、闸门、去重、裁决、产出报告 |

**为什么用 `reviewer`**：它是内置 agent 中唯一"只读（无 `write`、无 `bash`）+ 带 `contact_supervisor`"的角色。`scout`/`worker`/`delegate` 都带 `write`，不适合只读审计。**不要用 external-CLI agent**——本机 `claude-code`/`codex-exec`/`cursor-agent` 均报 `external-cli missing`，不可用。

**模型必须显式传**：所有内置 agent 默认继承会话模型（= `dimeta-domestic/deepseek-v4.1-flash`），所以一批必须显式传 `model: "dimeta-openai/gpt-6.1-sol"`，否则两批会变成同一个模型。

### B2. 批次一：发现（并行）

形状：`runs.all([...14 个 {key, agent:'reviewer', model:'dimeta-openai/gpt-6.1-sol', output:'...'}, ...])`
——一次并发拉起 14 个只读子智能体，每个只拿到自己区的 brief。

每个 brief 的固定契约（缺一不可）：

```text
目标      在本区（J<n> <名称>）内查找 AI Slop，产出一条一条可复核的发现。
范围      只读以下路径：<本区 globs>。不得读取或引用其他区的实现文件。
权限      只读。禁止修改任何文件、禁止 git 操作、禁止运行子智能体。
判据      使用 A–K 分类法（见 2026-10-12-ai-slop-audit.md 第 2 节）。
禁止标记  <逐字注入 A2 全文>
不变量    <逐字注入本区归属的不变量与出处>
输出      每条发现：文件:符号 | 逐字引用 | 判据编号 | 删掉谁受损 | 证据强度 | 复核方式
         跨区牵连只写一行 pointer → <目标区>。
停止      本区文件读完或发现数稳定即停；不要为了凑数扩大范围。
```

输出绑定用 `output`（运行时写入文件），**不靠 task 文本里的文件名**。

### B3. 闸门：引用校验（父在主线程执行，二批之前）

**这是整个工作流的关键闸门。** 逐条机械校验每个发现的引用：

1. 文件是否存在（`git ls-files` 精确匹配）。
2. 引用的符号名是否真的在该文件中定义或出现。
3. 引用的原文是否**逐字**出现在该文件里（去掉空白归一化后匹配）。

不通过的发现**不进二批**，标记为 `citation-failed` 并单独列出。没有这个闸门，二批会在编造的位置上建整栋分析。

### B4. 批次二：分析（并行）

输入：通过闸门的发现，按**牵连关系聚类**（不是按区），每簇一个分析者。数量 N 由聚类结果决定。

职责：分析该 slop **若被修复会影响什么**——涉及哪个不变量、哪条契约、哪个测试、哪个 ADR、哪个区。

三条硬约束：

1. **对抗性**：必须尝试**降级或反驳**每条发现（"这条其实是必需的防御"、"判据编号用错了"、"这是风格偏好不是 slop"）。只准附和的分析者没有价值。
2. **一跳限制**：只分析该 slop 的直接牵连，不得从一个 slop 跳到另一个 slop，不得顺着 ADR 往架构上游扩张。
3. **不修改代码**，只产出"牵连图 + 建议的处理顺序 + 风险"。

### B5. 去重与合并

去重键：`(区号, 文件, 符号, 判据编号)`。同一符号被两个区各自报一次时，保留**归属区**的那条，另一条降级为 pointer。

### B6. 落地物

- `slop-findings.jsonl`（每条一行，可统计、可 diff、可续跑）
- `slop-report.md`（人可读：按严重度与区排序，含闸门结果与二批牵连图）
- 统计与快照只写进带日期的报告，**不写进常驻文档**

## C. 这个工作流的漏洞与优化

### C1. 漏洞

| # | 漏洞 | 后果 | 处理 |
| --- | --- | --- | --- |
| **H1** | **子智能体之间无法互相通信。** 你设想的"汇报给负责那个区域的智能体"在架构上不可用：子智能体只能经 `contact_supervisor` 向**父**汇报；`intercom` 是**本地会话之间**的能力，而子智能体是 worker run，不是可寻址会话。且它们 `fresh` 上下文、生命周期有限，一批的 J4 说话时 J7 可能还没起来或已结束 | 跨区牵连丢失，或退化成在任务文本里空喊 | 改 **hub-and-spoke**：子 → 父，父用 `runs.steer(key, msg)` 转发给对应区。这恰好等价于你说的"一般只做汇报，不回复" |
| **H2** | 跨区牵连**不必**在一批内实时转发 | 增加一批的往返与抖动 | 跨区 pointer 统一进二批的聚类输入；只有当牵连**会改变另一区 agent 本人的判断**时才实时转发 |
| **H3** | **引用幻觉会被二批放大** | 在编造的位置上建整栋分析，产出看起来严谨但无根据的结论 | B3 引用校验闸门（**最高优先级**） |
| **H4** | 二批若只"解释"就会**放大**一批的错误而非澄清 | 报告质量低于单模型单遍 | B4 对抗性要求 + 父做抽样复核 |
| **H5** | 跨区重复报告（J7/J8 都看组件，J1/J2/J3 争同一 AI 边界） | 同一问题计 3 次，统计失真 | B5 去重键 + A4 只报本区证据 |
| **H6** | **禁止标记清单必须逐字注入**，否则模型会热情地把安全边界报成 slop（"这个校验重复了"、"这个 try/catch 多余"） | **误报导致真实损害**——比漏报严重得多 | A2 逐字注入每个 brief；父在裁决时对此类发现零容忍 |
| **H7** | 两批模型不同、口径未校准 | 二批把一批的 P3 噪音当 P1 深挖 | 先跑 pilot 校准，再放全量 |
| **H8** | "分析背后牵扯的东西"没有停止条件 | 无限深挖，成本失控 | B4 一跳限制 |
| **H9** | 上下文预算：J8/J13/J14 单区 3.5k–7k 行 | 区太大读不完，结论变浅 | J13/J14 已拆分；J8 若吃力再拆；brief 要求先 grep/ls 定位再读 |
| **H10** | 只读性没强制 | 审计期间工作区被污染 | 只用 `reviewer`；brief 写死禁止修改与 git；父保持工作区干净 |
| **H11** | 子智能体最终输出可能被截断 | 发现丢失 | `output` 绑定文件 + JSONL 累积 |
| **H12** | **编排者与二批同模型**（都是 `deepseek-v4.1-flash`） | 共享同样的盲点，看似交叉验证实则同源 | 明确这是"同模型不同上下文"的独立复核，不是跨模型验证；关键裁决抽查由一批模型（gpt-6.1-sol）复看 |

### C2. 优化

| # | 优化 | 收益 |
| --- | --- | --- |
| **O1** | 父在主线程**先跑零依赖确定性检测器**，把结果作为"已知事实"注入 brief | 减少 LLM 工作量；二批拿到可复核的机械证据；本就计划固化为 `npm run check:slop` |
| **O2** | 一批与二批之间加**引用校验闸门** | 掐断幻觉传播链（=H3） |
| **O3** | 二批**对抗性**设计 | 把"解释者"变成"反驳者"，修复 H4 |
| **O4** | **先 pilot**：1 个小区（J2 护栏，1,419 LOC）+ 1 个二批分析者 | 用最小成本校准两批口径，再决定是否放全量；也验证 `output`、`contact_supervisor`、只读约束真的生效 |
| **O5** | 把两个角色写成**项目级 agent 配置**（`slop-scout` = gpt-6.1-sol + 只读 + 禁止标记清单预置；`slop-analyst` = deepseek-v4.1-flash） | 模型/工具策略变成可审阅的声明式配置，不埋在启动脚本里；也符合"模型名属于部署策略"的原则。**需要你授权写配置** |
| **O6** | 一批 14 个 agent 一次并发 vs 分 2–3 波 | 受并发上限与配额约束未知，建议先 pilot 再决定批次大小 |
| **O7** | 用 `runs.lanes` 吗？**不用。** | 二批按"牵连簇"聚合，天然跨区，不是每 lane 顺序阶段；普通 `runs.all` + barrier 更贴合 |
| **O8** | 先执行 `action:"validate"` 静态校验工作流脚本 | **零启动**的免费检查，作为授权后的第一步 |

### C3. 授权后的执行顺序

```text
1. action:"validate" 校验工作流脚本（零启动、零副作用）
2. pilot：J2（护栏）单区发现 + 单簇分析，人工核对两批口径
3. 视 pilot 结果修正 brief 与判据，再放 14 区全量一批
4. 引用校验闸门 → 聚类 → 二批分析
5. 父仲裁、去重、抽样复核 → JSONL + 报告
6. 报告交你审阅；是否固化门禁、是否开栈 PR，另行决定
```

### C4. 需要你确认

1. **`reviewer` 作为两批的唯一角色**是否接受（内置里另一个只读选项是 `oracle`，但它是 `fork` 上下文且无 `contact_supervisor`）。
2. **H1 的 hub-and-spoke 替代方案**是否接受（子→父→转发，而非子↔子）。
3. **pilot 优先**是否接受，还是直接全量 14 区。
4. **是否授权 O5**（写项目级 agent 配置以固化模型与只读策略）。
5. **一批并发 14 个**是否合意，或分批（受未知并发上限约束）。
