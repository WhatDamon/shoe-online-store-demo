# Evoloop SEO / GEO 解决与优化方案

编写日期：2026-09-28。目标站点：https://evoloop.site。

本文是实施方案，不代表相关功能已发布或搜索效果已经改善。本轮只更新本文档，不修改业务代码、数据库、生产配置或交易流程。

## 1. 要解决什么

先把网站变成一本“信息真实、目录清楚、每件商品说得明白”的产品手册，再让搜索引擎和 AI 有机会找到、理解并引用它。

- SEO：用户搜索品牌、鞋款、尺码等问题时，能找到相应网页。
- GEO：这里指生成式搜索优化，让 AI 回答问题时有准确、可核实的品牌和商品页面可以引用。不是地理位置优化，也不是给网站加聊天框。
- 第一阶段先验收基础问题是否解决，后续观察搜索访问和咨询；不承诺排名、收录时间或 AI 推荐次数。

## 2. 当前状态与边界

### 2.1 已知情况

| 来源 | 可以确认 | 不能据此推断 |
| --- | --- | --- |
| 前次线上审计记录 | 曾发现分享图片使用 localhost、缺少 canonical/结构化数据，robots、sitemap、llms 路径返回 404 | 不能当作今天线上仍然如此的证明；发布前重新 GET 检查 |
| 2026-09-28 本地复核 | 已有 metadata、robots、sitemap、JSON-LD、FAQ 和 llms.txt 草稿，部分文件尚未提交 | 文件存在不等于配置正确，更不等于已上线 |
| 商品与内容资料 | 品牌宣传、演示状态、供应商资料、尺码和性能描述需要对齐 | 不能自动认定所有商品均为自研制造、3D 打印或已可购买 |
| 前次验证记录 | SEO 草稿验证曾被 spawn EPERM 和缓存目录访问问题阻断 | 项目原有测试基线通过，不代表本次草稿已通过生产构建 |

本轮没有完成官网实时复测，线上问题按“历史发现、待复核”管理。

### 2.2 优化顺序

| 顺序 | 接地气的解释 | 改善目标 |
| --- | --- | --- |
| 1 | 网站一会儿像演示项目，一会儿像营业品牌；宣传可能超出资料 | 首页、商品、文章、FAQ、机器数据说法一致且有依据 |
| 2 | 给搜索引擎看的地址和目录还不够可靠 | 正式地址正确，目录不含私人、失效或重复页面 |
| 3 | 用户想知道怎么选码、适合什么场景，却需要拼凑信息 | 一个页面能看懂事实、限制和下一步行动 |
| 4 | 本地改了，但缺少上线核验和反馈 | 有测试、发布记录、线上验收及观察指标 |

这是 SEO/GEO 工作顺序，不替代 AGENTS.md 的 P1 安全整改优先级。真实交易、报价和库存标记上线前，仍须满足已有安全与交易边界要求。

## 3. 第一阶段：先把事实和基础技术修准确

建议 2–3 个工作日；资料确认耗时另计。负责人：前端开发 + 品牌/商品负责人。

### 3.1 建立“网站事实表”

每条记录：事实名称、适用商品、权威来源、证据地址、确认人、确认时间、允许使用的文案。

- 当前是展示 demo、开放咨询、预售还是正式交易？不能仅凭后台存在订单接口判断营业状态。
- 商品是自研、供应商采购还是概念样品？品牌与制造商是否同一主体？
- 哪些部位使用何种工艺？资料中的 printedUpper: false 不能支持“所有鞋面均为 3D 打印”。
- 真实材质、尺码范围、颜色、场景和保养方式分别是什么？不同型号不能套用未经确认的尺码建议。
- “碳中和”“轻 30%”“数千份足部扫描”“医疗改善”等是否有适用范围、方法及公开证据？无法证明的删掉，或改成可验证的具体事实。

获确认的品牌信息和营业状态集中维护，由首页、FAQ、metadata、JSON-LD 复用；llms.txt 若保留也要一致。不得编造地址、作者、测试结果、评价或售后政策。

验收：抽查首页、三个商品和两篇文章，同一事实没有矛盾；性能/环保数字能追溯证据；未确认字段不作为事实发布。

### 3.2 正式网址、页面标题与分享信息

涉及：src/lib/seo.ts、src/lib/site.ts、.env.example、根 layout、首页、shop、blog、商品和文章页面。实施前阅读当前安装的 Next.js metadata 文档。

1. 生产站点使用已确认的 HTTPS 正式域名；环境配置去除多余空格、校验地址。生产误填 localhost/回环地址时明确报错，开发环境单独允许本地地址。
2. 可收录页面输出自己的 canonical，避免错误继承首页地址；不需要 canonical 的私有工具页不指向首页。
3. 页面标题、描述、OG、Twitter 分享内容一致；商品分享优先使用自身真实主图。为当前 metadata 合并逻辑补描述和图片继承测试。
4. 盘点 HTTP、www 等实际存在的入口，再重定向至主入口；不凭空新增域名。

兼容性：保留现有商品和文章 URL；必须更名时列出逐一永久重定向。新增环境变量同步 README、类型和测试。

验收：代表页面实际响应中没有 localhost，独立描述生效，分享图返回 200。检查 HTML、响应头和渲染结果，不能只在框架脚本字符串里找到字段就算通过。

### 3.3 哪些页面可以被收录

| 页面 | 设计策略 | 进入 sitemap |
| --- | --- | --- |
| 首页、shop、blog | 可抓取、可收录，canonical 指向自身 | 是 |
| 有真实资料的商品和文章 | 可抓取、可收录，canonical 指向自身 | 是 |
| 站内搜索结果 | noindex；允许爬虫读取标记 | 否 |
| 仅改变排序的重复页面 | 规范化到对应内容主页面 | 否 |
| 独立且内容充实的分类 | 稳定地址、独立文案、自身 canonical，按需求建设 | 满足条件后加入 |
| 任意筛选组合 | 不批量开放收录，按内容是否独立制定规则，不全部指向首页 | 否 |
| 购物车、结账、收藏公开外壳 | noindex 且允许读取标记；个性化数据受权限保护 | 否 |
| 订单与私人数据 | 先校验身份和所有权，未授权不返回私密内容；附加 noindex | 否 |
| API、测试/预览环境 | API 按用途控制抓取；非公开预览优先访问限制，附加 noindex | 否 |

涉及：src/app/robots.ts、src/app/sitemap.ts 及相关页面。Disallow 是“不准抓取”，不等于“禁止收录”；屏蔽抓取会让爬虫读不到 noindex。[2] 不能为读取标记而开放订单数据，robots 也不是权限系统。

网站地图只列正式、200、允许收录的 canonical 地址。当前固定日期和商品 createdAt 不能充当所有页面的真实修改时间：有可靠更新时间才填 lastModified，没有就省略。[3] 规定新增、下架和修改后的缓存刷新时限；数据库失败要报警，不能静默发布空地图。

验收：robots、sitemap GET 返回 200 且类型正确；地图没有工具、私人和失效链接。无效商品/文章尽量返回正确 404/410；若有框架流式响应限制，单独核验 noindex 和实际索引行为，不能输出假商品数据。

### 3.4 结构化数据只表达已核实事实

涉及：src/lib/structured-data.ts、src/components/seo/、商品和文章来源。

- Organization：稳定 ID、真实名称、官网及真实 logo；分享大图不当然等于 logo。仓库链接仅在确实代表品牌身份时用于 sameAs。
- Product：名称、图、品牌和可证实规格与页面一致；不能因为品牌叫 Evoloop，就自动声明制造商也是 Evoloop。
- Article：真实且可见的署名、发布日期和修改日期；团队署名如实表达，不虚构专家或每次构建刷新日期。
- BreadcrumbList：符合真实层级和页面链接。
- Offer：仅在真实交易启用、页面可见且数据来自权威交易目录后添加价格/库存。展示种子价不是实时售价，不虚构折扣到期日、评分或评论。

验收：JSON-LD 安全序列化、可解析，每个字段对应可见内容及来源。Schema 合法与富结果资格是两回事；demo 缺交易/评价资料时，不为通过富结果测试捏造字段。

## 4. 第二阶段：把页面做成真正有用的答案

建议 3–5 个工作日，资料与实拍另计。负责人：内容/商品负责人 + 前端开发。先改已有页面，避免新增大量薄内容。

### 4.1 首页

顺序：一句话说明卖什么/服务谁 → 明示营业状态 → 3–6 个真实代表商品及直达链接 → 实拍或资料证明差异 → 常见问题和详细页链接。没有证据不写性能数字，按钮与营业状态对应。

### 4.2 商品页

顺序：明确简介 → 实拍/细节图 → 规格表 → 尺码测量 → 适合及不适合场景 → 保养 → 3–5 个常见问题 → 对应状态的行动按钮。

- 逐款维护材质、颜色、尺码体系、工艺及来源；未知信息不靠模板补齐。
- 尺码说明包含测量步骤、单位和适用型号；不要全部建议“大半码”。
- demo 明示哪些资料仅展示，不暗示可支付；真实销售的交期、运费、退货与实际执行一致。
- 图片有描述性 alt、明确尺寸、适当压缩；首屏主图与下方画廊区别加载。先测移动端实际瓶颈，再决定优化。
- 关键文字在公开页面可读，不只放在图片或聊天里。不能将所有 Client Component 认定为不可抓取，应检查实际渲染。

### 4.3 文章与品牌信息

优先完善现有 /blog/ 的四类主题：尺码测量、不同脚型的选择限制、材质与保养、真实制造/供货流程。有对应文章就更新原 URL，暂不重复新建 /guides/。

文章结构：开头直接回答 → 适用条件/例外 → 步骤或对比表 → 实拍、测试或引用 → 真实署名与更新时间 → 相关商品和尺码链接。通用研究不能自动证明本品牌商品有相同效果，不批量生成换关键词的近似文章。

按真实状态补齐品牌介绍、联系方式、交付及退换货说明，页脚和商品页可达；无实体门店不强加 LocalBusiness，无实际服务不写承诺。

验收：先完成首页、三个代表商品、两篇核心文章；每页有明确问题、可信答案和下一步链接。其余商品先核查事实，模板通过后再扩展。

## 5. GEO 应该投入在哪里

优先做真实正文、清楚的商品事实、独立页面、可靠引用和一致品牌信息。Google 官方说明，AI 搜索功能沿用 SEO 基础，没有必须新增的特殊 AI 文件或专用结构化数据。[1]

纠正旧方案中的两点：

- llms.txt 降为可选实验。Google 在 2026-06-15 明确说明，它不是 Google Search 必需文件，不会正面或负面影响其可见性或排名。其他系统是否采用需另行验证；文件文字不能控制 AI，也不保证引用。[4]
- 保留有用 FAQ，取消“FAQ 富结果覆盖率”指标。Google 自 2026-05-07 起不再展示 FAQ 富结果。FAQ 的实施理由是帮助用户获取答案，而非获得这类搜索展示。[4]

不默认放开所有自称 AI 的爬虫；按平台官方文档区分搜索抓取、训练、用户触发访问，再结合站点策略决定。

## 6. 第三阶段：发布和验收

建议 1–2 个工作日。负责人：开发/部署负责人；站点所有者负责 Search Console、Bing Webmaster Tools 账户及域名验证。

### 6.1 发布前

- SEO 实施形成可审查提交，不无意混入、覆盖或回滚现有 AGENTS.md 和其他业务改动。
- Next.js 页面、metadata、Route Handler 实施前阅读当前安装版本文档。
- 补测域名校验、metadata 合并、canonical、noindex、JSON-LD 转义、sitemap 增删和异常路径。
- 代码实施后按项目要求执行 npm run verify、npm run build 及 AGENTS.md 列出的验收命令，记录环境、退出码和失败原因。未执行或被阻断不登记为通过；涉及 commerce/AI 时追加相应集成、所有权和并发测试。
- 本轮只改方案文档，运行目标 Markdown 格式检查与内容复核；运行时验收属于后续代码实施。

### 6.2 发布后

| 检查 | 方法 | 通过标准 |
| --- | --- | --- |
| 首页、shop、三个商品、两篇文章 | GET 正式 URL，检查响应及渲染 | 200、正文完整、独立标题描述、正确 canonical/分享图 |
| robots、sitemap | GET、解析、抽样请求地图地址 | 规则正确，无私人、失效地址或错误域名 |
| 工具和订单页 | 匿名及授权会话分别检查 | 索引策略符合设计，未授权拿不到私人数据 |
| 不存在/下架地址 | 请求错误 handle/slug 和下架样本 | 正确错误/下架策略，无假商品 JSON-LD，不在地图中 |
| 结构化数据 | Schema 校验，适用页面做 Rich Results Test | 无语法/事实错误，按实际资格解释测试结果 |
| 缓存刷新 | 测试环境新增、修改、下架样本 | 正文、索引规则和地图按规定时限更新 |
| 搜索平台 | 验证站点、提交地图、检查代表 URL | 抓取和索引资格符合设计；提交不保证收录 |
| 移动端 | 检查首屏、图、按钮、布局和性能 | 无影响阅读/操作的故障，与基线比较 |

正式站复测发现历史问题已解决时，记录证据并跳过，不重复改造。

监测公开页面与 sitemap 状态码、生成失败、资料缺失和异常域名；持续 5xx、全站意外 noindex 等及时通知维护人。日志不记录令牌或订单敏感内容。保留版本、发布时间、改动列表，不用爬虫访问次数代替优化效果。

## 7. 第四阶段：用 4–8 周看效果，再扩展

先记录可获得的发布前 28 天基线；不足就从发布日起建立，明确样本量。按等长窗口比较，记录同期投放、促销等干扰。

| 目标 | 指标 | 注意 |
| --- | --- | --- |
| 页面被找到 | 有效公开页、实际收录、错误/重复 canonical | 配置合格不保证全部收录 |
| 获得相关访问 | 品牌/非品牌展示、点击、点击率、着陆页 | 按目标市场/语言分组，不只看一个关键词名次 |
| 用户继续行动 | 看商品、用尺码页、咨询、真实购买 | demo 的模拟订单不计收入 |
| AI 事实准确 | 固定问题中的引用页、品牌/尺码/营业状态准确性 | 每周记录平台、日期、语言、联网状态及可见模型；是抽样诊断，不是市场份额 |
| AI 带来访问 | 可识别 AI 引荐及后续行动 | 无 referrer 的访问无法完整归因 |

首批问题可用“Evoloop 是什么”“现在能否购买”“某款如何选码”“哪些型号适合某场景”，采用目标受众实际语言。Google AI 搜索访问包含在 Search Console 整体 Web 报告中，不声称能从中完整单独统计。[1]

依据数据决定下一批：有需求的独立分类、被访问的尺码内容、高关注商品的实拍与资料。先验证有用，再扩数量。

## 8. 交付顺序、依赖和回滚

| 阶段 | 交付物 | 完成门槛 |
| --- | --- | --- |
| 第一阶段 | 事实表、URL 策略、基础技术修正 | 事实确认，技术验收通过 |
| 第二阶段 | 首页、代表商品、核心文章、必要服务说明 | 内容与真实状态一致，有依据 |
| 第三阶段 | 可审查版本、部署记录、线上核验、平台提交、监测 | 相关测试/构建通过，阻断项解决 |
| 第四阶段 | 基线、每周样本、4–8 周复盘及下一批任务 | 采集有效数据，不用排名承诺验收 |

首轮预计 6–10 个工作日，是任务估算；资料补齐、环境故障和交易安全整改另计。人手有限时，先事实确认与技术基础，再做三个代表商品和两篇核心文章。

本方案不引入迁移。代码实施按阶段提交并保留前一部署版本；异常时回退本次发布，复测 canonical、noindex、robots、sitemap 与公开正文。不得回退无关安全修复或整体清空工作区。未来如新增更新时间字段，另行设计迁移、兼容和回滚后再实施。

暂缓：无依据性能宣传、虚假评论、批量关键词文章、为富结果捏造价格库存、重复 guides 目录、将 llms.txt 当主要增长项目。
